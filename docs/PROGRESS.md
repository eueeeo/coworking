## 6. Анализ схемы базы данных (из субд.drawio.pdf)

### 6.1 Таблицы, поля и связи (прочитаны из PDF)

| Таблица | Поля | Ключи |
|---|---|---|
| **Роли** | Код роли, Название | PK: Код роли |
| **Пользователи** | Код пользователя, Код роли, ФИО, Электронная почта, Телефон, Хэш пароля, Активность | PK: Код пользователя; FK: Код роли |
| **Статусы бронирований** | Код статуса, Название | PK: Код статуса |
| **Зоны** | Код зоны, Название, Этаж, Описание | PK: Код зоны |
| **Типы рабочих мест** | Код типа, Название, Описание, Цена за час | PK: Код типа |
| **Рабочие места** | Код места, Код зоны, Код типа, Номер места, Описание, Активность | PK: Код места; FK: Код зоны, Код типа |
| **Удобства** | Код удобства, Название | PK: Код удобства |
| **Удобства рабочих мест** | Код места, Код удобства | PK+FK: Код места; PK+FK: Код удобства (связующая таблица) |
| **Бронирования** | Код бронирования, Код пользователя, Код места, Код статуса, Начало бронирования, Окончание бронирования, Стоимость, Дата создания | PK: Код бронирования; FK: Код пользователя, Код места, Код статуса |

**Связи (кардинальность из диаграммы: 1 и N маркеры):**
- Роли (1) ← (N) Пользователи
- Зоны (1) ← (N) Рабочие места
- Типы рабочих мест (1) ← (N) Рабочие места
- Рабочие места (1) ← (N) Бронирования
- Пользователи (1) ← (N) Бронирования
- Статусы бронирований (1) ← (N) Бронирования
- Рабочие места (M) ↔ (N) Удобства (через таблицу Удобства рабочих мест)

### 6.3 Недостатки и замечания по схеме

#### Обязательные исправления (по логике бизнес-требований):

| # | Проблема | Обоснование |
|---|---|---|
| 1 | **Роли:** лучше хранить как перечисление, а не отдельную таблицу с FK, учитывая что ролей всего 2 | При Entity Framework Core удобнее `ENUM('Администратор', 'Клиент')` или `TINYINT`; таблица Роли допустима, но создаёт избыточный JOIN при каждом запросе пользователя |
| 2 | **Бронирования.Стоимость** — вычисляемое поле | Стоимость должна рассчитываться (ЦенаЗаЧас × Длительность в часах). Хранение в таблице — денормализация (обоснована: фиксирует стоимость на момент бронирования) |
| 3 | **Поле ФИО в Пользователях** — атомарность | По 3НФ ФИО стоит разделить на Фамилию, Имя, Отчество. Однако задание явно указывает «ФИО» — компромисс допустим при явном обосновании |
| 4 | **Этаж в Зонах** — тип данных | Этаж должен быть числовым (INT), а не строковым, для корректной сортировки |
| 5 | **Отсутствует ограничение** `CHECK (Окончание > Начало)` | Бизнес-правило: окончание позже начала — должно быть реализовано на уровне СУБД |

#### Рекомендации (не обязательны по заданию):

| # | Рекомендация | Обоснование |
|---|---|---|
| 1 | Добавить `UNIQUE(Электронная почта)` в Пользователях | Предотвращает дублирование аккаунтов |
| 2 | Добавить `UNIQUE(Номер места, Код зоны)` в Рабочих местах | Номер места уникален в рамках зоны |
| 3 | Добавить триггер или CHECK для запрета пересечения бронирований | Бизнес-правило из методички |
| 4 | Индексы на FK-поля (Код роли, Код зоны, Код типа, Код места, Код статуса) | Производительность JOIN-запросов |
| 5 | `NOT NULL` на все обязательные поля | Целостность данных |

### 6.4 Проверка 3НФ

- **1НФ:** Все атрибуты атомарны ✅ (кроме дискуссионного ФИО — см. выше)
- **2НФ:** В связующей таблице `Удобства рабочих мест` нет неключевых атрибутов, зависящих от части составного ключа ✅
- **3НФ:** Все неключевые атрибуты зависят непосредственно от первичного ключа своей таблицы ✅ (`Стоимость` в Бронированиях — обоснованная денормализация)

### 6.5 Проверка бизнес-правил бронирования

| Правило | Схема | Реализация |
|---|---|---|
| Окончание > Начало | Поля Начало/Окончание есть | ❌ Ограничение CHECK отсутствует в диаграмме |
| Запрет пересечений | — | ❌ Не отражено в схеме (нужен триггер или CHECK CONSTRAINT) |
| Только активные места | Поле Активность в Рабочих местах ✅ | Нужна проверка в приложении + при бронировании |
| Только активные пользователи | Поле Активность в Пользователях ✅ | Нужна проверка при входе |

### 6.6 Вопросы, требующие уточнения

1. **Таблица Роли** — оставлять как отдельную таблицу с FK или использовать ENUM в таблице Пользователей?
2. **ФИО** — одно поле или три (Фамилия, Имя, Отчество)?
3. **Статусы бронирований** — исходная схема предполагает 4 значения: «Подтверждено», «Активно», «Завершено», «Отменено». Нужен ли начальный статус «Новое» (до подтверждения администратором)?
4. **Этаж** — хранить в Зонах или вынести в отдельную таблицу Этажи?

### 6.7 Предлагаемая исправленная структура (в именах SQL)
